# 수행 사례 게시 요구사항

> 외주 발주자가 회사의 수행 이력을 사이트에서 확인하고, 위시켓·크몽 지원서에서 사례 링크로 바로 들어올 수 있게 한다.

**작성일**: 2026-11-15
**버전**: 0.1.0
**상태**: Draft (사용자 검토 대기)
**대상 릴리스**: v3.3.0

---

## 1. 배경

- 2026-11-15 사용자 결정: 사이트 개선의 목표는 「외주 수주용 회사 소개 강화」이고, 첫 항목은 「수행 사례 23건 게시」다.
- 위시켓에는 포트폴리오 23건이 등록되어 있다. 목록의 단일 출처는 `scout-agent/packages/wishket-form/catalog.mjs` 의 `CATALOG` 이다.
- 사이트의 출시 프로젝트 탭(`/projects`, `ReleasedTab`)은 D1 `portfolio_items` 를 읽는다. 코드에서 확인되는 등록 데이터는 EasyWord 1건(`cloudflare-workers/migrations/0012_add_easyword_portfolio.sql`)뿐이다. 운영 D1 의 실제 건수는 이 문서를 쓴 환경에서 조회하지 못했다.
- 발주자가 지원서를 보고 회사를 검색해도 수행 이력을 확인할 페이지가 없다.

## 2. 사용자 스토리

| 번호 | 사용자 | 원하는 것 | 이유 |
|------|--------|-----------|------|
| US-1 | 외주 발주자 | 자기 과업과 비슷한 수행 사례를 목록에서 찾는다 | 맡길 수 있는 회사인지 판단하려고 |
| US-2 | 외주 발주자 | 사례 하나의 과제, 해결 방법, 결과를 읽는다 | 지원서에 적힌 내용을 검증하려고 |
| US-3 | 지원서 작성자(scout) | 사례마다 고정된 주소를 지원서에 붙인다 | 첨부 포트폴리오와 같은 사례를 사이트에서도 보여 주려고 |
| US-4 | 발주자 | 사례를 읽은 뒤 바로 문의한다 | 다른 페이지를 찾지 않고 연락하려고 |

## 3. 기능 요구사항

### FR-1 사례 데이터
- 위시켓 포트폴리오 23건을 `portfolio_items` 에 등록한다. 이미 등록된 EasyWord(목록 4번)는 새로 만들지 않고 내용을 보강한다.
- 사례마다 제목, 요약, 분야, 과제, 해결 방법, 결과, 사용 기술, 수행 시기, 맡은 역할을 둔다.
- 사례마다 `CATALOG` 의 번호(1~23)를 기록한다. scout 가 고른 포트폴리오와 사이트 사례를 번호로 대응시키기 위해서다.
- slug 는 한 번 정하면 바꾸지 않는다. 지원서에 붙은 링크가 끊어지면 안 되기 때문이다.

### FR-2 사례 목록
- `/projects` 의 출시 탭에서 사례를 분야별로 걸러 볼 수 있다. 분야 분류는 5개 안팎으로 한다(예: AI·문서지능, 데이터 플랫폼, 커머스·결제, 앱 서비스, 설계·컨설팅).
- 카드에는 제목, 한 줄 요약, 분야, 수행 시기를 보여 준다.

### FR-3 사례 상세
- `/projects/:slug` 에서 과제, 해결 방법, 결과를 차례로 보여 준다. `Project` 타입에 이미 있는 `problem`·`solution`·`impact` 필드와 같은 구성을 쓴다.
- 상세 하단에 문의 버튼(`/connect/inquiry`)을 둔다. 문의 폼에는 어느 사례에서 왔는지가 함께 전달된다.
- 사례마다 제목과 설명 메타 태그, Open Graph 태그를 둔다. 메신저나 지원서에서 링크를 열기 전에 내용이 보여야 하기 때문이다.

### FR-4 지원서 연결 (scout 쪽, 이 명세의 범위 밖)
- scout 지원서에 사례 링크를 넣는 일은 scout-agent SPEC 의 F-item 으로 따로 다룬다. 이 명세는 번호와 slug 의 대응표를 제공하는 데까지만 책임진다.

## 4. 제약

- 고객사 이름과 미공개 수치는 사용자 확인 없이 싣지 않는다. 기본값은 익명 표기(예: 「의료원」, 「보험대리점」)이고 `CATALOG` 제목의 수준을 넘지 않는다.
- 제안·설계 단계의 사례(목록 3·14·15·18·22번처럼 제목에 「설계」「제안」이 붙은 것)는 구축 사례와 구분해서 표기한다.
- 사례 본문의 사실 관계는 사용자가 제공한 자료로만 쓴다. 자료가 없는 항목은 비워 두고 게시하지 않는다.
- 경력 원장은 비공개 원본이다. 리포에는 공개 가능한 칸만 옮기고, 출처 구분·기관명·정확한 규모 수치는 넣지 않는다.
- 사례마다 수행 단계(구축·운영, 프로토타입·PoC, 설계, 제안, 화면 시안)를 카드와 상세에 표시한다. 원장의 「쓰지 않는 내용」(must_not_claim)을 본문이 어기지 않는지 게시 전에 검사한다.
- 구현 규모 수치는 원장이 정한 둥근 표현으로만 쓴다.
- 스키마 변경은 열 추가만 한다. 기존 `portfolio_items` 행과 관리자 화면(`AdminPortfolio`)이 그대로 동작해야 한다.
- 배포는 기존 방식(main 머지 → Cloudflare Pages, Workers 는 `wrangler deploy`)을 따른다.
